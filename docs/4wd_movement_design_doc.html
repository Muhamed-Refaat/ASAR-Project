Left side (L298N #1): IN1=LOW, IN2=HIGH, IN3=LOW, IN4=HIGH
Inverted from forward. PWM magnitude = abs(−V) on ENA (pin 5) and ENB (pin 6).
Right side (L298N #2): IN1=LOW, IN2=HIGH, IN3=LOW, IN4=HIGH
Inverted from forward. PWM magnitude = abs(−V) on ENA (pin 8) and ENB (pin 9).
Sign handling: The Mega firmware converts the signed SPD value into direction bits + unsigned PWM magnitude. Never pass a negative value directly to analogWrite().

Rotation not working? The most common cause is the right-side direction bits being wrong. Verify IN pins 36–39 against the hardware spec. If the robot arcs instead of pivoting, one motor pair polarity is inverted — correct with motor terminal swap, not firmware.

Root causes of jitter during forward motion

1
Joystick deadband missing or too small
Small center-drift on the Blynk joystick generates tiny nonzero X values. The differential mix converts these into left ≠ right commands. The robot constantly micro-corrects, producing jitter.
// In ESP32 differential mix:
const int DEADBAND = 10; // tune 5–15
if (abs(x) < DEADBAND) x = 0;
if (abs(y) < DEADBAND) y = 0;
int left = constrain(y + x/2, -255, 255);
int right = constrain(y - x/2, -255, 255);
2
SPD command flooding — sending too fast
Blynk joystick events fire at 50ms. If every tiny XY change sends a new SPD, the Mega receives dozens of micro-corrections per second. Add a change threshold before transmitting.
// Only send if command changed significantly:
if (abs(newLeft - lastLeft) > 3 ||
abs(newRight - lastRight) > 3) {
sendSPD(newLeft, newRight);
lastLeft = newLeft; lastRight = newRight;
}
3
Mismatched motor polarity causing oscillation
If one side's IN pins are wired backward, the Mega tries to go forward while the firmware simultaneously corrects, producing rapid direction flips. Test each motor side with motor_tst.ino in isolation before using SPD commands.
4
PWM too low — motors stall and restart
Below a motor-specific minimum PWM (often 60–80 for cheap DC motors), motors receive insufficient voltage to overcome static friction and stall. The result looks like jitter. Enforce a minimum output when nonzero.
// In Mega setMotorSpeed helper:
const int MIN_PWM = 70;
int applyMin(int pwm) {
if (pwm == 0) return 0;
return (pwm > 0) ? max(pwm, MIN_PWM)
: min(pwm, -MIN_PWM);
}
5
UART parse errors causing spurious STOP commands
Partial line delivery or a noisy UART2 link can cause the Mega to receive malformed frames. It responds with ERR and falls to safe-stop, interrupting forward motion intermittently. Check for shared GND between ESP32 and Mega, and verify your line buffer is flushed correctly on newline.

Rotate not working — checklist

Check: are you sending SPD:+V:−V or LEFT:V?
The LEFT:V command uses a predefined turn behavior (arc, not pivot). For true in-place rotation you must use SPD:+V:−V explicitly.
Check: right side IN pins 36–39 in firmware
If right-side IN pins are inverted in firmware, SPD:+V:−V sends both sides forward → straight ahead, not pivot. Verify mega.ino right-side direction logic against hardware spec pins 36–39.
Check: motor polarity confirmed with motor_tst.ino first
Run T01 from the validation spec before testing SPD commands. Hardware polarity and firmware direction bits must be confirmed in isolation before combining.
Quick pivot test: Send SPD:150:-150 from the serial monitor. Both sides should visibly spin in opposite directions (left forward, right backward). If the robot drifts forward instead, the right side direction bits are wrong. If it spins in the wrong rotational direction, swap left and right in the command.
